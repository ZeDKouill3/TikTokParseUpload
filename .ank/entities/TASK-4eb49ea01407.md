  SPEC-6127 (qa.status passed | rejected, jamais prêt si rejected), ADR-ad2e. Décision utilisateur 2026-09-29 : un clip rejeté casse toute sa série (les parties se suivent), donc qa ne rejette que si le clip est incompréhensible ou techniquement cassé. Aujourd'hui qa rejette dès qu'il y a un défaut (status = rejected if issues) : sur sZi-qJ-5ptA, 00-p1 (starts_mid_sentence) a tué une série de 9 parties et 01-p2 (écran noir 1,2 s, transition du docu) une série de 3. Attendu : chaque issue porte severity = blocking | warning ; status = rejected seulement s'il y a au moins une issue blocking ; les warnings restent dans qa.issues (le clip reste prêt). Nouveau défaut LLM 'incomprehensible' (blocking) : sans ce qui précède dans la vidéo, le spectateur ne comprend pas de qui ou de quoi il s'agit, ou l'histoire du clip ne se suit pas. starts_mid_sentence et weak_hook deviennent warning (face_cut et subtitle_on_face : warning aussi). Contrôles locaux : durée réelle ≠ JSON, résolution fausse et silence initial restent blocking ; écran noir blocking seulement à partir de black_block_seconds (nouveau réglage, 3 s par défaut), warning entre black_min_seconds et ce seuil. Le prompt explique que seul incomprehensible est bloquant et qu'une partie 2+ d'une série peut supposer les parties précédentes (elle n'est pas incompréhensible pour ça). Séries : après le contrôle de toutes les parties d'un moment multipart, si une partie est rejected, chaque autre partie reçoit une issue warning 'series_part_rejected' qui nomme la partie rejetée. Tests : starts_mid_sentence seul -> passed avec warning ; incomprehensible -> rejected ; noir 1,2 s -> passed avec warning ; noir 4 s -> rejected ; résolution fausse -> rejected ; partie 2 rejetée d'une série de 3 -> parties 1 et 3 passed avec warning series_part_rejected ; toute la suite pytest reste verte.
