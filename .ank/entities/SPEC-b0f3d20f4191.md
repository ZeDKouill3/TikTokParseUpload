## Objet
Deux nouveaux styles « Twitch gaming » (format stream, comme le style twitch) et « Letterbox gaming » (format letterbox, comme le style classic) partagent un **jury axé action** : une grille embarquée `builtin:gaming-action` et des candidats qui ne viennent pas seulement de la transcription (étape `action`, ADR-4e57). Les styles existants (twitch = stream + builtin:gaming ; classic = letterbox + builtin) restent inchangés pour comparer les vues. Cette SPEC complète SPEC-9216 (grilles embarquées) et SPEC-4063 (grille v4, règles de sélection) sans les remplacer : `builtin` et `builtin:gaming` restent identiques octet pour octet.

## Grille gaming-action
R1. Grille embarquée. `[moments] rubric_path` accepte en plus « builtin:gaming-action » (clipper/assets/rubric-gaming-action.toml). L'erreur d'un « builtin:<inconnu> » liste les trois grilles. Même validation (`load_rubric`) ; fichier commenté en français, aucun nom réel de chaîne ni de personne ; inclus dans le paquet installé.
R2. Valeurs : min_score 50, max_moments_per_hour 6, always_keep_score 70, min_moments_cap 3 ; trend_keywords vide. Critères et poids :
- action 5 : « Se passe-t-il quelque chose DANS LE JEU pendant le clip : combat, clutch, mort, victoire ou défaite, sursaut, retournement, moment de jeu spectaculaire ? 0-2 si rien ne se passe dans le jeu (menu, chargement, le streamer commente, donne son avis ou raconte sa vie). »
- emotion 3 : « Réaction forte AU JEU : cri, rire, rage, peur, sursaut, soulagement, hurlement de victoire ou de défaite ? »
- hook 2, payoff 2, standalone 1, value 0, trend 0 (questions de la grille gaming).
Durées : single_min 20, single_max 90, part_min 30, part_max 90, min_parts 2, max_parts 12, tolerance 3. [bonus] et [exclusions] identiques à la grille gaming. Plus la table `[gate]` de R3 : criterion = "action", min = 4, unless_criterion = "emotion", unless_min = 8.
R3. Seuil éliminatoire `[gate]` (table OPTIONNELLE de toute grille ; absente, aucun effet : builtin et builtin:gaming n'en ont pas). Un candidat dont la note au critère `criterion` (note agrégée du jury en sélection jury, note du proposeur sinon) est strictement inférieure à `min` est rejeté avec la raison « <criterion> <note> < seuil éliminatoire <min> (grille) », sauf si sa note à `unless_criterion` est ≥ `unless_min` (la « réaction forte » qui sauve un monologue). Appliqué dans l'étape moments avant le filtre min_score, listé dans `rejected` avec notes et justification ; la re-notation après vision (`rescored`) le conserve. Validation par `load_rubric` : `criterion` et `unless_criterion` doivent nommer un critère de [criteria], `min` et `unless_min` des entiers de 0 à 10 ; `unless_criterion` et `unless_min` vont ensemble (les deux ou aucun) ; toute faute est une MomentsError qui nomme la clé.

## Étape action (clipper/action.py)
R4. Place et entrées. `pipeline.STEPS` = download, transcribe, audio, scenes, action, moments, vision, parts, captions, reframe, subtitles, render, qa (audio AVANT scenes ; action entre scenes et moments). Entrées : audio.json, scenes.json, transcript.json, meta.json (`duration`) ; absentes alors que l'étape est activée : ActionError explicite. Résultat déjà présent (action.json) : non refait sauf `force`.
R4bis. Fenêtres de pics dans scenes (ADR-4e57 point 2). `scenes.detect_scenes` reçoit `peak_windows: bool = False`, positionné par clipper.pipeline seul à la valeur de `[action] enabled` (scenes ne lit la config d'aucune autre étape). À False : audio.json est ignoré même présent ; les fenêtres décodées, les plans, les images et scenes.json sont identiques octet pour octet à aujourd'hui (aucune clé ajoutée). À True : audio.json est une entrée obligatoire (absente : ScenesError) ; chaque pic hors parole élargit les fenêtres décodées de `speech_margin_seconds` de chaque côté (code existant de `_speech_windows`) ; scenes.json porte `"peak_windows": true`. L'étape action, activée, exige `scenes.json["peak_windows"] is True` ; sinon ActionError : « scenes.json produit sans fenêtres de pics : relancer scenes avec --force (style avec [action] enabled = true) ».
R5. Réglages, dans CONFIG_DEFAULTS de clipper/action.py (table `[action]` de config.toml et des presets) : enabled false ; window_seconds 30 ; step_seconds 15 ; audio_weight 1.0 ; audio_peaks_full 3 ; audio_peak_min_db 6.0 ; cuts_weight 1.0 ; cuts_ratio_full 3.0 ; min_score 0.6 ; max_passage_seconds 90 ; max_passages_per_hour 12 ; frames_per_passage 4 ; max_images_per_hour 48 ; batch_size 8 ; max_width 768 ; parallel 4. Toute valeur invalide (bornes : window > 0, 0 < step ≤ window, poids ≥ 0 et somme > 0, *_full > 0, 0 < min_score ≤ 1, max_passage ≥ window, entiers ≥ 1 pour les plafonds, batch et parallel) est une ActionError qui nomme la clé.
R6. Détection déterministe (aucun LLM). Fenêtres de `window_seconds` tous les `step_seconds` de 0 à `duration`. Par fenêtre : audio_peaks = pics d'audio.json de relative_db ≥ audio_peak_min_db dans la fenêtre (nombre, max relative_db) ; scene_cuts = débuts de plans de scenes.json dans la fenêtre ; scene_cuts_ratio = scene_cuts / médiane des scene_cuts de toutes les fenêtres (médiane nulle : ratio = scene_cuts) ; speech_ratio = durée des segments de transcript.json dans la fenêtre / window_seconds. Score = (audio_weight x min(1, audio_peaks / audio_peaks_full) + cuts_weight x min(1, scene_cuts_ratio / cuts_ratio_full)) / (audio_weight + cuts_weight). Les fenêtres de score ≥ min_score qui se chevauchent ou se touchent fusionnent en un passage ; un passage plus long que max_passage_seconds est coupé en passages de max_passage_seconds au plus, alignés sur ses fenêtres les mieux notées ; score du passage = max de ses fenêtres, signaux = somme (pics, coupes) et moyenne (speech_ratio). Classement par score décroissant puis start ; au plus ceil(max_passages_per_hour x duration / 3600) passages gardés, les autres dans `rejected` avec la raison « plafond max_passages_per_hour ». Aucun passage : action.json écrit avec `passages: []`, aucun appel LLM, ligne INFO.
R7. Images. Pour chaque passage gardé, `frames_per_passage` images de scenes.json `frames` dont le timecode est dans le passage, les plus proches des instants start + k x durée / (n + 1), sans doublon ; moins d'images disponibles : on prend ce qu'il y a ; aucune : `frames: []`, `frames_missing: true`, ligne WARNING (l'étape n'extrait jamais d'image elle-même, ADR-4e57). Plafond : images totales ≤ ceil(max_images_per_hour x duration / 3600) ; les passages pris dans l'ordre du classement, celui qui ferait dépasser le plafond et les suivants sont rejetés avec la raison « plafond max_images_per_hour ».
R8. Description par le LLM. Images triées par timecode, lots de `batch_size`, une planche par lot (clipper/montage.py : grille horizontale, chaque image réduite à `max_width` sans agrandissement, légende « Image <index> : <timecode> s » ; même rendu que vision, qui l'utilise désormais aussi), un seul fichier image par appel `llm.ask("action", ...)` (usage `action`, modèle fast par défaut dans clipper.llm CONFIG_DEFAULTS usages). Réponse par image (index) : description (1 phrase, ≤ 300 caractères), action_type parmi combat, clutch, mort, victoire, defaite, retournement, sursaut, exploration, menu_ou_chargement, webcam_ou_chat_seul, autre ; intensity entier 0-10. Index manquant ou en double : SchemaError. Lots jusqu'à `parallel` à la fois, chaque lot réussi écrit dans action_partial.json (atomique, verrou) et relu à la relance ; dossier temporaire des planches supprimé en fin d'étape, originaux intacts. Réponse invalide ou LLM indisponible : l'erreur remonte, action.json n'est pas écrit (ADR-ad2e).
R9. Sortie `workspace/<video_id>/action.json` : {"video_id", "enabled", "settings": {toutes les clés de R5 effectives}, "passages": [{"id": "a<n>", "start", "end" (centième), "duration", "score", "signals": {"audio_peaks", "audio_peak_max_db", "scene_cuts", "scene_cuts_ratio", "speech_ratio"}, "frames": [{"timecode", "path", "description", "action_type", "intensity"}], "frames_missing"}], "rejected": [{"start", "end", "score", "signals", "reason"}], "llm_calls", "images_sent"}. Désactivée (`enabled = false`) : {"video_id", "enabled": false, "passages": [], "rejected": [], "llm_calls": 0, "images_sent": 0}, sans lire audio/scenes ni appeler le LLM.

## Étape moments : candidats d'action
R10. Réglage `[moments] candidates` : "transcript" (défaut : sorties identiques à aujourd'hui, prompts compris) ou "transcript+action". Autre valeur : MomentsError. En « transcript+action » : action.json requis et `enabled` true, sinon MomentsError nommant le fichier ou « [action] enabled » (jamais de repli sur la seule transcription).
R11. Chaque passage d'action.json devient un candidat de source « action », format single, sans appel LLM pour ses bornes : chaque borne est recalée sur la frontière de phrase (début de phrase pour start, fin pour end) la plus proche si elle est à moins de `[moments] action_snap_seconds` (défaut 3) ; sinon gardée telle quelle (centième supérieur, SPEC-4063 règle 5). Les connecteurs de tête (leading_connectors) sont retirés comme pour un candidat de la transcription quand la borne start tombe sur une phrase. hook_text = texte de la première phrase incluse (connecteurs retirés) ou, sans parole, la description de l'image la plus intense du passage. Les règles de grille s'appliquent ensuite à l'identique : SponsorBlock, durée (single_min..single_max ± tolerance ; un passage plus long que single_max est rejeté pour durée, comme un candidat de la transcription), dédoublonnage sur les bornes.
R12. Matière donnée aux noteurs pour un candidat d'action (proposeur, tour de comparaison et jury) : « Parole : "<texte des phrases incluses>" » ou « Parole : (aucune) » ; « Signaux : <audio_peaks> pics audio (max +<db> dB), <scene_cuts> changements de plan (x <ratio> la médiane de la vidéo), parole <speech_ratio> % » ; « Images : <timecode> s : <description> (<action_type>, intensité <n>/10) ; ... ». Le texte d'un candidat de la transcription ne change pas. Le prompt du proposeur reçoit en plus, dans les signaux mesurés, la liste des passages d'action (bornes, score, types d'action) pour qu'il puisse aussi proposer dessus.
R13. Notation. Sélection « jury » : les candidats d'action sont notés avec les autres dans le même passage de jury (aucun appel de plus). Sélection « single » : un appel `moments` supplémentaire note les seuls candidats d'action avec le prompt et le schéma du tour de comparaison existant (`_comparison_prompt`, `comparison_schema`), leur matière de R12 tenant lieu de texte. Bonus mesurés, [gate] (R3), min_score, non-chevauchement et plafond souple sont communs ; entre un candidat d'action et un candidat de la transcription qui se chevauchent, SPEC-4063 règle 4 s'applique (multipart d'abord, puis le mieux noté).
R14. moments.json : chaque moment et chaque rejet noté porte `"source": "transcript" | "action"` ; un candidat d'action garde `"action": {"id", "score", "signals", "frames": [timecodes]}`. La re-notation après vision (`_rescore`) retrouve les bornes d'un candidat d'action telles qu'enregistrées (pas d'exigence de frontière de phrase pour lui) et réapplique [gate].

## Styles et console
R15. Clés des deux presets (fichiers locaux presets/<nom>.toml, créés par l'orchestrateur, jamais commités) :
- Twitch gaming : [channel] (source_url, display_name, logo au choix) ; [reframe] layout = "stream_auto", stream_variant = "split", fallback = "blur" et les tables split_webcam_dest / split_gameplay_dest / split_subtitle_dest / badge_dest du style twitch ; [render] comme le style twitch (title_enabled, cta_enabled, badge_*) ; [moments] rubric_path = "builtin:gaming-action", candidates = "transcript+action" (short_clips au choix ; avec short_clips = true, mettre [action] max_passage_seconds ≤ short_max, sinon tout passage d'action plus long est rejeté pour durée) ; [action] enabled = true.
- Letterbox gaming : [channel] ; [moments] rubric_path = "builtin:gaming-action", candidates = "transcript+action" ; [action] enabled = true ; aucune table [reframe] (letterbox par défaut, comme classic).
Aucune clé [scenes] à ajouter : `[action] enabled` pilote seul les fenêtres de pics (R4bis). Les styles twitch et classic (sans [action]) produisent les mêmes scenes.json, moments.json et clips qu'aujourd'hui.
R16. Console (SPEC-9216 R4 étendue) : le choix « Grille de notation » propose Standard / Gaming / Gaming action / Fichier personnalisé ; `_rubric_info` rend kind « gaming-action », libellé « Gaming action (<valeur>) », et reconnaît un fichier identique à cette grille ; la section « Grille de notation et moments » du formulaire de style expose `[moments] candidates` et `action_snap_seconds`, et une section « Action (passages de jeu) » expose la table `[action]` (au moins `enabled`) ; enregistrer un style depuis la console conserve ses tables [moments] et [action] ; la fiche vidéo indique, pour chaque moment, sa source (transcription ou action).

## Tests et coût
R17. Tests sans réseau, CPU, FakeBackend seulement : fixtures synthétiques (audio.json, scenes.json avec frames JPEG minuscules générées, transcript.json) ; chaque règle R1-R16 a au moins un test ; tests de non-régression des témoins : avec `[action] enabled = false`, scenes.json est identique octet pour octet à celui produit sans audio.json (audio.json présent, `peak_windows` False), et avec `candidates = "transcript"` moments.json et les prompts envoyés sont identiques à avant. Test réel optionnel (`tests/test_action_real.py`) : sauté sauf `CLIPPER_ACTION_REAL=1` ; lit `CLIPPER_ACTION_REAL_VIDEO` (chemin d'un extrait de VOD ≤ 10 min) ; enchaîne audio, scenes, action puis moments en « transcript+action » avec la config réelle ; vérifie action.json (≥ 1 passage avec images décrites, `images_sent` ≤ plafond) et qu'au moins un candidat de source action est noté ; jamais lancé par défaut ni en CI.
R18. Coût borné par heure de VOD : appels `action` ≤ ceil(ceil(max_images_per_hour x h) / batch_size) (défauts : 6/h) ; proposeur et jury : même nombre d'appels qu'aujourd'hui, prompts plus longs ; sélection single : + 1 appel `moments` par vidéo. `llm_calls` et `images_sent` d'action.json et llm_usage.jsonl mesurent le réel.
